FAQ

How the tracker works

How the shared data is refreshed, why updates are deliberately paced, and what the historical timestamps actually mean.

How is the site synced?

Simply opening the website does not send fresh requests to Wise Old Man or Temple. The pages first read the group’s saved shared baseline, with the repository snapshot and browser storage available as fallbacks. Fresh external requests only happen when an update button is used. After a successful update, the new shared document is saved so everybody sees the same baseline.

Why does a WOM refresh take a while?

This is deliberate. The site refreshes the five members one after another rather than firing everything at WOM at once. For each member, every outbound WOM request waits 3.2 seconds before it is sent. A refresh can request the current profile, new snapshot-history pages, achievements, and week, month and year gains. That means a full group refresh can easily take more than a minute.

The pacing is intentionally conservative so the tracker does not hammer WOM, hit rate limits, or risk temporary blocking. Each successful member is saved independently, so if a later member fails, earlier successful updates are not lost.

What does “WOM accuracy ±…” mean?

WOM snapshots are checkpoints, not a continuous recording of the account. For a level reconstructed by the tracker, it compares two consecutive saved snapshots. If the earlier snapshot says level 92 and the next says level 93, the tracker knows the level happened somewhere between those two timestamps, but not the exact minute.

The code calculates the displayed ± value as half of the time between those snapshots. For example, if the snapshots are 8 hours apart, the Chronicle shows ±4h. The event is currently displayed at the later snapshot time, so the ± figure should be read as a shorthand for “this was inferred from an 8-hour snapshot window”, not as a statistical confidence interval. More frequent WOM snapshots produce smaller uncertainty windows.

How is the Collection Log synced?

Collection Log data comes from Temple. The server requests the five player logs in small batches with a maximum concurrency of two and a short stagger between requests. It also retrieves recent item unlocks separately. If a player request fails or returns an invalid log, the tracker keeps that player’s last known good saved log rather than treating the missing response as zero progress.

What happens if WOM cannot update a player?

The WOM refresh first tries to request an updated player profile. If that update request fails, it falls back to reading WOM’s latest already-tracked profile. History, achievements or gain-period requests can also fail independently; in those cases the tracker keeps the last successful saved values instead of wiping them.

Why can historical dates be approximate?

The tracker can only place an event exactly when the source itself provides a usable event timestamp. Many historical levels are reconstructed from changes between WOM snapshots. The wider the gap between those checkpoints, the wider the possible time window in which the level was actually gained.

What does Total Collection Log Value mean?

It is the estimated Grand Exchange value of the quantities stored in each member’s saved Collection Log. The group total and contribution split use the same valuation logic as Collection Log Advanced. Items without a usable trade price contribute 0 gp, with a few special item states valued from their tradeable components.

Does the site refresh automatically?

No. Normal page visits use saved data and do not repeatedly contact WOM or Temple. The manual update buttons are what deliberately start fresh source requests. This keeps the site fast for normal browsing and avoids unnecessary API traffic.

What does the member filter affect?

The selected members control comparisons, charts and Collection Log views throughout the site. Group-wide masthead totals continue to use the full five-member group where applicable.
