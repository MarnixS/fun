FAQ

How the tracker works

How the shared data is refreshed, why updates are deliberately paced, and what the historical timestamps actually mean.

Does opening the site hit the WOM or Temple APIs?

No. Normal browsing is deliberately separated from external API traffic. Opening a page, switching menus, viewing charts or checking the Collection Log does not trigger a fresh WOM or Temple update. The site loads the already-saved shared group data itself and renders the pages from that baseline.

The shared baseline is the normal source for the whole site, with the repository snapshot and browser storage available as fallbacks. Fresh WOM or Temple requests only start when somebody explicitly presses an update button. Once an update succeeds, that new shared document becomes the baseline everybody loads. This design means ten people can browse the site without creating ten separate bursts of requests to WOM or Temple.

Why does a WOM refresh take a while?

Because the tracker is intentionally polite to the WOM API. It refreshes the five members one after another instead of firing a large burst of requests. Before every outbound WOM request, the code waits 3.2 seconds. A single member can require the current profile, one or more new snapshot-history pages, achievements, and week, month and year gain data, so a complete five-player refresh can easily take more than a minute.

That delay is a feature, not a performance problem. The site is deliberately designed to trade a little refresh speed for fewer requests per second, lower load on WOM and a much smaller chance of hitting rate limits or being temporarily blocked. Normal page loads still use the saved baseline instantly, so this slower process only happens when somebody explicitly asks for fresh data.

Each successful member is also saved independently. If member five fails after the first four succeed, those first four updates remain saved instead of the entire refresh being thrown away.

What does “WOM accuracy ±…” mean?

WOM snapshots are checkpoints, not a continuous recording of the account. For a level reconstructed by the tracker, it compares two consecutive saved snapshots. If the earlier snapshot says level 92 and the next says level 93, the tracker knows the level happened somewhere between those two timestamps, but not the exact minute.

The code calculates the displayed ± value as half of the time between those snapshots. For example, if the snapshots are 8 hours apart, the Chronicle shows ±4h. The event is currently displayed at the later snapshot time, so the ± figure should be read as a shorthand for “this was inferred from an 8-hour snapshot window”, not as a statistical confidence interval. More frequent WOM snapshots produce smaller uncertainty windows.

How is the Collection Log synced without hammering Temple?

Collection Log data comes from Temple, but it is not fetched again every time somebody opens the site. Normal browsing uses the saved shared Collection Log. A fresh Temple update is only requested when the update button is pressed.

When that happens, the server requests the five player logs in small batches with a maximum concurrency of two and a short stagger between requests instead of sending all requests at once. Recent item unlocks are retrieved separately using the same restrained approach. If a player request fails or returns an invalid log, the tracker keeps that player’s last known good saved log rather than treating the missing response as zero progress.

I got a drop and updated Temple. Why isn’t it showing on the site?

Temple can only show Collection Log data that your game client has actually sent to it. If you got a new drop, first open your Collection Log in game and click the refresh button inside the Collection Log. That pushes the latest Collection Log state out from the client side.

After that has been refreshed in game, use Update Collection Log via Temple on this site. The site can then pull the newer Temple data into the shared baseline. If you only press the website’s Temple button without first refreshing the Collection Log in game, Temple may still be serving the older log and there is nothing newer for this site to import yet.

What happens if WOM cannot update a player?

The WOM refresh first tries to request an updated player profile. If that update request fails, it falls back to reading WOM’s latest already-tracked profile. History, achievements or gain-period requests can also fail independently; in those cases the tracker keeps the last successful saved values instead of wiping them.

Why can historical dates be approximate?

The tracker can only place an event exactly when the source itself provides a usable event timestamp. Many historical levels are reconstructed from changes between WOM snapshots. The wider the gap between those checkpoints, the wider the possible time window in which the level was actually gained.

What does Total Collection Log Value mean?

The quantities come from each member’s saved Collection Log, but the prices are checked live against the OSRS Wiki price API when the page loads. For normally tradeable items, the tracker uses the current Wiki high/low prices: if both are available it uses their midpoint; if only one side is available it uses that price. The group total and each player’s percentage are then recalculated from those current prices.

Some Collection Log drops are untradeable components, so they need a derived value instead of a direct GE price. The tracker values an Araxyte fang as the current value of an Amulet of rancour minus an Amulet of torture. Each Noxious point, blade or pommel is valued at one third of a Noxious halberd. Each Soulreaper axe piece (Executioner’s axe head, Eye of the Duke, Siren’s staff or Leviathan’s lure) is valued at one quarter of a Soulreaper axe.

The four Desert Treasure II vestiges use the same residual-value idea. Bellator, Magus, Venator and Ultor vestiges are valued as: current finished ring value minus the corresponding Dagannoth Kings ring, minus 500 blood runes, minus 3 chromium ingots. This estimates the value attributable specifically to the vestige instead of pretending the untradeable vestige itself has a normal GE price. Any remaining item without a usable direct or derived price contributes 0 gp.

Does the site refresh automatically?

No external API refresh happens automatically. The site itself loads and reuses the latest saved WOM and Temple documents so pages can work normally without repeatedly asking third-party services for the same information. Only the manual update buttons deliberately start fresh source requests. This is one of the main protections against unnecessary API traffic and accidental request spam.

What does the member filter affect?

The selected members control comparisons, charts and Collection Log views throughout the site. Group-wide masthead totals continue to use the full five-member group where applicable.
